# Phase 30.2 — Checkout et webhook (le crédit ne vient que du webhook)

**Branche :** `{{BRANCH}}` · **Migration réservée :** `{{MIGRATION}}` · **Base :** `{{PARENT}}`

## Objectif

Construire le dos de la boutique : une session Stripe Checkout créée côté serveur, un webhook
vérifié sur le **corps brut**, et une écriture de `currency_ledger` idempotente. La route de
checkout ne crédite **jamais** : seul le webhook crédite. Sans clés Stripe, tout répond
`503 SHOP_DISABLED`.

Cette phase suppose la vague 1 fusionnée : `packages/shared/src/packs.ts` et la migration
`0013_shop` (index partiel `currency_ledger_purchase_uniq`) existent.

## Décisions déjà prises

1. **Interface pure dans `packages/shared/src/payments.ts`** : `CheckoutInput`, `CheckoutSession`,
   `PaymentEvent`, `PaymentProvider`. Aucun type Stripe dans le shared.
2. **Implémentation Stripe dans `apps/api/src/services/stripe-payments.ts`**, avec le SDK
   `stripe` ajouté à `apps/api/package.json`. Le client est créé paresseusement : l'API doit
   démarrer sans clés.
3. **Deux plugins de route**, pour que le webhook soit public et le checkout protégé :
   - `shopCheckoutRoutes(provider)` : `POST /shop/checkout`, `GET /shop/orders/:id`.
   - `shopWebhookRoutes(provider)` : `POST /shop/webhook`.
   `createApp({ paymentProvider })` choisit le provider ; `app` reste l'export par défaut.
4. **Référence du ledger = identifiant de session Checkout** : `PURCHASE:<session.id>`. Le
   remboursement (phase 30.3) réutilisera le même identifiant. C'est ce qui rend
   `GET /shop/orders/:id` simple : `id` est le `session_id` de l'URL de succès.
5. **Aucune écriture au ledger dans `/shop/checkout`.** La réponse est `{ url }` uniquement.
6. **Le webhook lit le corps brut.** Un corps déjà parsé casse `stripe.webhooks.constructEvent`.
   Utiliser un hook `onParse` `{ as: 'scoped' }` sur le plugin webhook qui rend
   `request.text()` pour le chemin `/shop/webhook`, puis déclarer `body: t.String()`.
7. **Idempotence** : `insert into currency_ledger … on conflict do nothing` sur
   `PURCHASE:<sessionId>`, dans une transaction qui verrouille `"user"` en `FOR UPDATE` et ne
   met à jour `"user".currency` que si l'insertion a réellement eu lieu.
8. **Devise et montant** : le client n'envoie qu'une `packKey`. Le serveur relit `packs.ts`.
   Le montant Stripe vient du `STRIPE_PRICE_*` serveur ; le nombre d'écus vient du catalogue,
   jamais de `amount_total`.
9. **Variables optionnelles** : `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`,
   `STRIPE_PRICE_PACK_500`, `STRIPE_PRICE_PACK_1200`, `STRIPE_PRICE_PACK_2500`,
   `STRIPE_PRICE_PACK_6000`. Si l'une manque **ou est vide**, `ShopDisabledError` →
   `503 SHOP_DISABLED`. Une chaîne vide vaut absente : tester `if (!value)`, pas
   `value !== undefined`.
10. **Aucun appel réseau dans les tests.** Un `FakePaymentProvider` signe et vérifie en mémoire.

## Pièges

- **Le piège n°1 est le corps brut.** Si `body` arrive déjà parsé, la signature échoue. Écris
  d'abord le test qui envoie une chaîne JSON exacte avec une signature calculée sur cette
  chaîne, puis fais passer le hook `onParse`. Ne "corrige" pas en désactivant la vérification.
- `onConflict((oc) => oc.doNothing())` sans colonnes est le plus sûr avec un index partiel.
- `"user".currency` est nullable : utiliser `coalesce(currency, 0)` dans la mise à jour.
- Le webhook doit répondre `200` à un utilisateur inconnu ou à un pack inconnu (journaliser,
  ignorer) : un `400` ferait réessayer Stripe indéfiniment.
- Ne crédite jamais sur `amount_total` : un client peut choisir un autre pack, pas un autre
  montant ; le nombre d'écus est `pack.ecus`.
- Ne monte pas le webhook dans le groupe protégé : Stripe n'a pas de cookie de session.
- Ne touche pas encore au plafond quotidien ni aux remboursements : c'est la phase 30.3.

## Critères d'acceptation

1. `/shop/checkout` ne crée aucune ligne de ledger.
2. Le webhook valide crédite une seule fois, même rejoué.
3. La signature invalide est refusée sans écriture.
4. Sans clés Stripe, les deux routes répondent `503 SHOP_DISABLED`.
5. `GET /shop/orders/:id` ne lit que le ledger de l'utilisateur courant.
6. Aucun appel réseau dans `packages/spec`.
7. `ci:check` vert.
